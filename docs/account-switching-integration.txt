公開状態
  ACCOUNT_SWITCHING_ENABLED は false。アカウント切り替えは利用者には未公開。
  通常ログイン・登録・ログアウトは既存authController/authServiceを使う。
  以下の接続コード・UIは実装したが、公開条件を満たしていないため有効化しない。
  フラグを true にするだけで公開完了と扱わないこと。

実装した接続
  supabaseClients.js: legacy・匿名公開・運営のSDK生成元。ページ内でキーごとに一つ。
  accountAuthController.js: 既存authView/メニューが利用する状態と操作を新runtimeへ接続。
  accountScopedClient.js: ENo/Auth ID/gameAccountId/SDKクライアントを固定。
    許可RPCのみ公開し、所有者指定引数を照合。読み書きをcoordinatorへ通す。
    古いコンテキストから新クライアントへ切り替わることはない。
    送信済み書き込みの完了時に選択状態が変わっていれば結果不明扱い。自動再送しない。
  accountSwitchView.js/commonMenu.js: 保存済み一覧、現在使用中、追加、再認証、未完了slot清掃。
    ログイン専用dialog、パスワード消去、Esc/キャンセル、フォーカス復帰、処理中無効化。
    ホームへの遷移はcontrollerに集約。

  通常ログイン・登録: 新モードでは旧キーへsignInせずmanagerへ委譲。

旧セッションとログアウト
  registry未作成時だけinitialize()が既存legacy SDKを検証して採用。
  トークンをコピーしない。セッションなしも空registryを書き、再採用を防ぐ。
  対象が曖昧/通信不明なら採用しない。
  既存registryの未選択状態は維持し、自動選択しない。
  ログアウトは選択中slotのみlocal scopeで処理。他slotを維持してホームへ遷移。
  期限切れslotの再認証は既存セッションが失効と確認できる場合だけ行う。

削除
  二段階確認を維持。managerが検証済みのENo/名前/gameAccountId/Auth IDを照合して削除RPC。
  正確に一致する削除完了応答を確認した後は、Authの消滅を削除失敗と解釈しない。
  清掃はそのslotのローカルログアウト・一覧除去のみ。他アカウントを選択しない。
  通信不明時は成功表示も自動再送もしない。

削除の永続復旧（2026-10-16追記）
  保存キー: diesduck-account-deletions-v1
  形式: {version:1, entries:[{slot, eno, gameAccountId, authUserId, state}]}
  state: deletion-pending / deletion-confirmed。最大50件、フィールド・ID・重複を検証。
  名前・パスワード・Authトークンは記録しない。トークンの管理は従来どおりSDKのみ。
  送信直前: 本人・ENo・名前・両IDを検証してpendingを書き、読み戻して確認する。
  書き込み失敗ならRPCは0回。送信後は同じ対象への再送を禁止する。
  正確に一致するdeleted:true応答だけをconfirmedとして永続化する。
  成功応答後でもconfirmedの保存に失敗した場合はpendingが残る。成功扱いにせず、
  次回のgetUser失敗・期限切れ・セッション不在からサーバー削除成功を推測しない。

  再読み込み後: runtime/controllerがjournalを読み、メニューへ復旧状況を渡す。
  confirmedには「端末側の処理を完了する」。押すと削除RPCなしで対象slotだけを清掃。
  SDK getSessionのuser IDとENo由来emailを照合し、別ユーザー・曖昧な状態なら拒否。
  明確なsession:nullならログアウト要求不要。それ以外はSDK signOut(scope:local)後に
  session:nullを再確認する。サーバー削除済みユーザーのgetUser成功を要求しない。
  一覧から対象slotのみ除去し、activeが対象の場合のみnull。他のactiveは保持する。
  一覧保存後にjournal除去が失敗した場合も、一覧にslotがない状態から再清掃可能。
  他slot/ENoとの再利用衝突があれば拒否。最後にSDK購読・非legacy更新・参照を解放。
  共有legacyクライアントの自動更新は止めない。

  pendingには結果不明の説明だけを表示し、再削除・再認証・通常保存を禁止する。
  pendingからの自動解決や「ログイン情報だけを除去する」操作は今回提供しない。
  サーバー状態の信頼できる照合手順がないため、管理者による状態確認が必要。
  他の正常なENoは選択して利用できる。清掃のため再びアカウント削除を押す必要はない。
  復旧操作もcoordinatorへ接続し、書き込み中・未保存変更のガードを通す。
  Web Locksは既存registryキーを共用。SDK awaitの後でregistry/journal/操作世代を再確認。
  storage通知時に古いleaseを無効化し、復旧一覧を更新する。
  ブラウザ記録は改変可能。認可や新たな削除成功証明には使わず、照合可能なslotの
  端末清掃のみに利用する。実際の削除は従来の本人確認付きRPCだけ。
